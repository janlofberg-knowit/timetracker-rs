# How to work

## Always
* Use conventional commits when committing code
* Follow existing project conventions unless instructed otherwise.
* Prefer correctness over cleverness.
* Keep changes focused on the requested task.
* Use ASD-STE100 Simplified Technical English for documentation and user-facing responses.
* Keep comments short and explain why, not what.
* Prefer code that is clear without comments.
* Verify changes with the appropriate build, test, or validation tools when available.
* State clearly when a change could not be verified.
* Preserve existing user changes.
* Prefer existing helpers
* Work using the DRY (Dont Repeat yourself) principle 
* Always keep method names obvious and clear, there should be no room for confusion.
* Break things out if a file grows too large, better with several small files with clear purposes than one big blobb

## Never 
* Never overwrite or discard existing user changes.
* Never invent APIs, assets, configuration values, commands, or project conventions.
* Never claim that code was built, tested, or verified when it was not.
* Never make unrelated changes while completing a task.
* Never name methods something obscure

## Testing 
* Keep code tests in their own files and folders instead of placing tests in module code files



## Comments

Keep comments concise, preferably under 50 characters.

Comments should explain intent or reasoning rather than restate the code. Move substantial explanations to the appropriate documentation file.
